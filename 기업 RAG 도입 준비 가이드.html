기업 RAG 도입, 담당자가 가장 먼저 준비할 것

RAG(검색 증강 생성)는 AI 모델이 답하기 전에 회사 문서를 먼저 찾아 읽게 하는 방식입니다. 도입의 성패는 모델 선택보다 어떤 질문에, 어떤 문서로, 누구에게 답할지를 정하는 준비에서 갈립니다.

핵심 요약

시스템을 고르기 전에 ① 풀 문제와 사용자, ② 문서 현황, ③ 접근 권한, ④ 정답 기준(평가 질문)을 먼저 확보하세요. 이 네 가지가 있으면 어떤 기술을 써도 PoC를 빠르게 검증할 수 있습니다.

1. 준비 순서

  1. 목표와 사용자 정하기

    "사내 규정 문의 응대 시간을 줄인다"처럼 한 문장으로 쓰고, 주 사용자(신입사원, 영업, 고객센터 등)와 성공 기준(응답 시간, 정확도, 문의 감소율)을 정합니다.

  2. 문서 목록(인벤토리) 만들기

    문서가 어디에 있는지(공유 드라이브, 위키, 메일, ERP), 형식(PDF, 문서, 표, 스캔본), 최신본 여부, 담당 부서를 표로 정리합니다.

  3. 보안·권한 기준 확정

    개인정보, 영업비밀, 인사정보가 섞여 있는지 분류하고, 직급·부서별로 볼 수 있는 문서를 구분합니다. 외부 클라우드 모델 사용 가능 여부도 이 단계에서 보안팀과 합의합니다.

  4. 문서 정리와 소유자 지정

    중복·구버전 문서를 걷어내고, 문서마다 제목, 개정일, 적용 대상 같은 메타데이터를 붙입니다. 문서가 바뀔 때 갱신할 담당자도 정합니다.

  5. 평가용 질문·정답 세트 만들기

    실제 사용자가 던질 질문 30~100개와 근거 문서, 기대 답변을 준비합니다. 이것이 PoC의 합격 기준이 됩니다.

  6. 작은 범위로 PoC

    한 부서, 한 문서군으로 시작해 검색 품질과 답변 정확도를 평가 세트로 측정하고, 임베딩 모델·청크 크기·검색 방식을 조정합니다.

  7. 운영 체계 설계

    문서 자동 갱신, 사용자 피드백 수집, 로그 점검, 비용 모니터링, 오답 신고 절차를 마련한 뒤 범위를 넓힙니다.

2. 기업 제공 예제: 한빛전자 사내 규정 도우미

아래는 설명을 위해 만든 가상의 사례입니다.

회사: 한빛전자 (직원 1,200명, 제조업)

문제: 인사팀·IT팀·품질팀에 규정 문의가 하루 평균 80건 들어오고, 대부분 문서에 이미 답이 있는 반복 질문이다.

목표: 6개월 안에 반복 문의 40% 감소, 답변에는 반드시 근거 문서와 조항을 표시.

담당자: 디지털혁신팀 김 과장 (인사·IT·품질·보안팀 담당자와 협업)

급여 기준표엑셀최신제한 (인사팀만)인사팀

이 표를 만들면서 담당자는 바로 결정할 일이 생깁니다. 구버전 규정은 제외하고, 스캔본은 OCR로 변환하며, 급여 기준표와 메일은 1차 범위에서 뺍니다. 1차 PoC 범위는 인사 규정 + IT 가이드로 좁힙니다.

② 문서 정리 규칙

  • 파일명을 "인사_휴가규정_v2025.03"처럼 통일하고, 구버전은 별도 폴더로 이동
  • 각 문서에 메타데이터 부여: 제목, 개정일, 적용 대상(정규직/계약직), 소유 부서
  • 조항 단위로 나누기(청킹): 조항이 중간에 잘리지 않도록 "제5조 연차휴가" 같은 제목 단위로 분할

마지막 두 질문은 답하면 안 되는 질문입니다. 평가 세트에는 정답이 있는 질문뿐 아니라, 권한이 없거나 문서에 없을 때 올바르게 거절하는지 확인하는 질문도 반드시 넣어야 합니다.

1차 결과가 기준에 못 미쳐도 실패가 아닙니다. 어떤 지표가 낮은지 보면 원인이 문서(구버전 혼재), 검색(청크 크기), 답변 지침(거절 규칙) 중 어디인지 알 수 있고, 평가 세트가 있기 때문에 고친 뒤 다시 측정할 수 있습니다.

3. 담당자 준비 체크리스트

  • 풀 문제, 사용자, 성공 지표를 한 문장으로 정리했다
  • 문서 인벤토리(위치·형식·최신 여부·소유 부서·민감도)를 만들었다
  • 보안팀과 외부 모델 사용 범위, 개인정보 처리 방침을 합의했다
  • 문서별 접근 권한 기준을 정했다
  • 구버전 정리와 메타데이터 부여 규칙을 정했다
  • 평가 질문 30개 이상(거절해야 할 질문 포함)을 준비했다
  • PoC 범위를 한 부서, 한 문서군으로 제한했다
  • 문서 갱신 담당자와 오답 신고 절차를 정했다

4. 자주 하는 실수

  • 문서 정리 없이 전부 투입: 구버전과 신버전이 섞이면 모델이 틀린 규정을 근거로 답합니다.
  • 권한을 나중에 고려: 검색 단계에서 권한을 걸러내지 않으면 접근 권한이 없는 정보가 답변에 노출될 수 있습니다.
  • 평가 기준 없이 "잘 되는 것 같다"로 판단: 데모에서 몇 개 질문이 잘 답해도 실제 운영 품질은 알 수 없습니다.
  • 처음부터 전사 확대: 작은 범위에서 검증하고 개선한 뒤 넓히는 편이 비용과 위험이 낮습니다.
  • 운영 담당자 부재: 문서는 계속 바뀌므로 갱신 책임자가 없으면 시간이 지날수록 답변 품질이 떨어집니다.
※ 한빛전자와 수치는 설명을 위한 가상 예시입니다. 실제 기준은 회사의 문서와 업무 환경에 맞게 조정하세요.
